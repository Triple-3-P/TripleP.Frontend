# Task Manager — Frontend API Layer (RTK Query + ASP.NET Core)

> Draft v0.1 · 2026-10-16 · **Design and reference code; no backend integration has been run.**
> Aligned with `api-contracts.md`, `openapi-p0-core.yaml`, `domain-model.md` and the FSD design.
> Adapted from the supplied reference skeleton; executable example files are not installed in this repository. See [adoption notes](implementation-plan.md) and [source disposition](source-import.md).

## 1. Decision summary

1. **Backend:** ASP.NET Core owns authentication, authorization, validation, workflow transitions, idempotency, audit, concurrency, and data persistence.
2. **Frontend:** Next.js App Router; RTK Query owns client-side server data and mutations. Server Components do not use Redux or RTK Query.
3. **Transport:** Browser uses **same-origin** `/api/v1`. In local development a Next.js rewrite forwards to .NET; production uses a trusted reverse proxy. This is _not_ automatically an auth/security boundary.
4. **Auth:** HttpOnly Secure SameSite=Lax session cookie issued by .NET. Avoid storing auth tokens in Redux/localStorage. .NET sets up antiforgery service, provides a readable **request** token and validates on every cookie-authenticated unsafe request, including login/logout.
5. **One API root:** one `baseApi = createApi({ endpoints: () => ({}) })` in `shared/api`; entity modules use `injectEndpoints`. Do not create a fresh `createApi` per FSD entity.
6. **Types:** initially reference types matching the draft OpenAPI. When the contract is frozen, use `openapi-typescript` to generate DTO/endpoint types from the **backend-published** OpenAPI, checked for drift against the reviewed contract.
7. **Concurrency:** `ETag` is opaque; user passes exact ETag via `If-Match`. For WorkItems `etag` exists in summary and detail DTOs. `412` is a conflict UI, not a request to blindly retry.
8. **Idempotency:** every logical creation/command request has an `Idempotency-Key` generated once when the user performs the operation and reused for safe transport retries; never regenerated by an automatic retry.
9. **Caching:** RTK Query tags by entity ID and scoped list ID; lists remain cursor-paginated. Realtime events invalidate affected tags rather than maintaining a second source of truth.
10. **Isolation:** clear RTK Query caches when session expires, logout succeeds, current tenant changes, or access is revoked. Scope all user-visible cache operations to the authorized context.

## 2. Component and request architecture

```text
Browser client (Next.js)
  React Client Components
    ↳ features/move-task, features/create-task (form logic, side effects)
       ↳ entities/work-item/api/work-item-api.ts
       ↳ entities/project/api/project-api.ts
       ↳ entities/workspace/api/workspace-api.ts
          ↳ shared/api/base-api.ts (one RTK Query API slice)
             ↳ fetchBaseQuery(credentials: same-origin)
                ↳ /api/v1/* (browser SAME ORIGIN)
                   ↳ reverse proxy / Next rewrite in development
                      ↳ ASP.NET Core API
                         ↳ auth + antiforgery + authorization + validation
                         ↳ domain commands + optimistic concurrency
                         ↳ PostgreSQL and outbox/events
```

A Next.js Route Handler BFF is **optional**, not the default. Add one only when needing server-only credentials, backend aggregation, or token exchanges. If deployed on multiple domains, use a proper ingress to keep browser calls same-origin; avoid `SameSite=None` and cross-origin credential complexity without reason.

In production, ensure reverse proxy forwards request headers (`If-Match`, `Idempotency-Key`, `X-CSRF-Token`, `X-Request-Id`), `Set-Cookie`, and response `ETag` unchanged. On ASP.NET Core configure trusted forwarded-header handling; restrict host/origin and redirects.

## 4. Auth and CSRF — two explicit flows

### Pre-authentication / Login

1. Browser opens login page. **Before** `POST /auth/login`, call `GET /api/v1/auth/csrf` to obtain `XSRF-TOKEN` request cookie. This endpoint is an **addition** to the previous OpenAPI draft.
2. JS reads only `XSRF-TOKEN` (not session cookie), sends its value as `X-CSRF-Token` on POST/PATCH/PUT/DELETE.
3. ASP.NET Core validates token + Origin where applicable and applies login throttling. On success sets HttpOnly Secure session cookie. Handle SameSite, Path and Domain consistently with proxy architecture.
4. Request a _new CSRF token_ after login/session identity transition. Then `GET /me` to bootstrap personalized UI.
5. `GET /me` returning 401 indicates unauthenticated. Redirect to login from an app-level handler. Do not attempt token refresh automatically unless a real refresh endpoint and replay semantics are agreed.

### Session lifecycle / Logout

- Explicit logout: `POST /auth/logout` with CSRF header; after confirmed success clear every RTK Query cache and navigate to auth screen.
- `401` on protected API: emit `sessionExpired` and clear all protected data. No replay of commands.
- `403`: show restricted action; do not clear unrelated caches, but invalidate capabilities for that resource.
- Access revoked / active Workspace changed: clear private cache (or remount Provider keyed by workspace if the UX guarantees this). Clear other persistent client stores, WebSocket subscription groups and files previews as needed.
- Unauthenticated endpoints (`/auth/login`, `/auth/register`) must not trigger a global logout action for their own 401 errors.

Example ASP.NET Core setup (illustrative, not a drop-in complete security pipeline):

```csharp
builder.Services.AddAntiforgery(x => x.HeaderName = "X-CSRF-Token");
app.MapGet("/api/v1/auth/csrf", (IAntiforgery antiforgery, HttpContext ctx) =>
{
    var tokens = antiforgery.GetAndStoreTokens(ctx);
    ctx.Response.Cookies.Append("XSRF-TOKEN", tokens.RequestToken!, new CookieOptions
    {
        Secure = true, HttpOnly = false, SameSite = SameSiteMode.Lax, Path = "/"
    });
    ctx.Response.Headers.CacheControl = "no-store";
    return Results.NoContent();
});
// IMPORTANT: separately register antiforgery validation on all relevant
// unsafe cookie-authenticated endpoints, including login and logout.
```

The **antiforgery validation cookie** and **authentication cookie** remain HttpOnly; only the _request token_ is JS-readable. Include tests for CSRF-negative requests, cookie path/domain, HTTPS reverse proxy, and login/logout rotations. Consider a signed token sent in a response body if cookie forwarding proves difficult; keep an explicit, uniform contract.

P1: Team, Sprint, Epic planning, Releases, Milestones, Calendar, Dashboards and Time Tracking use the **same** shared baseApi, new injected endpoint modules, and existing error/cookie conventions. P2: Documents, Forms, Automations, Integrations, Portfolios use the same transport but their DTOs are still drafts.

### Why not create separate `createApi` for each module?

RTK Query's automatic tag invalidation is scoped to one API slice. Splitting into many slices loses cross-module invalidation and adds middleware/reducer overhead. **Use one root with endpoint injection.** Lazy code-splitting remains available when needed.

## 6. Cache design

| Query                                                | Key                        | Provides                                        | Invalidated by                                       |
| ---------------------------------------------------- | -------------------------- | ----------------------------------------------- | ---------------------------------------------------- |
| `getMe()`                                            | no args                    | `Session`                                       | Login/logout/session changes                         |
| `listWorkspaces()`                                   | no args                    | `Workspace:LIST`, each workspace ID             | Workspace create/rename/archive                      |
| `listProjects({workspaceId})`                        | workspace UUID             | `WorkspaceProjects:{workspaceId}` + project IDs | Project changes, membership changes                  |
| `getProject(projectId)`                              | project UUID               | `Project:{projectId}`                           | Project update, membership/capabilities              |
| `listWorkItems({projectId,cursor,limit,...filters})` | full normalized query args | `WorkItemList:{projectId}` + item IDs           | Create/move/status/reorder/archive, relevant updates |
| `getWorkItem(itemId)`                                | stable UUID                | `WorkItem:{id}`                                 | Any detail-changing operation or realtime event      |
| `getStatuses(projectId)`                             | project UUID               | `WorkflowStatus:{projectId}`                    | Status CRUD/reorder/retire                           |
| `listComments({itemId,cursor})`                      | item and cursor            | `Comments:{itemId}`                             | Comment writes                                       |

Pagination: **each cursor page has its own cache key**. Do not merge pages by hand at first. Board/List URL parameters (`status`, `assignee`, `sort`, `view`) remain in `searchParams`; feed them into query args. Their server-side validation and caching behavior must match backend filters. For future infinite scroll, migrate to the RTK Query infinite-query API and update tests deliberately.

### Optimistic mutation: status change

1. Drag/drop handler checks `allowedTransitions` for preliminary UI affordance.
2. It sends exact current item `etag`, target status ID, and a new idempotency key.
3. Patch the visible detail cache plus **one** visible list page immediately; disable another mutation on this same WorkItem until resolution.
4. Backend checks permission, transition graph, `If-Match`, and idempotency atomically.
5. On success, upsert the returned server detail and invalidate all project list pages (other filters/views may differ).
6. On failure, invalidate detail/list caches and refetch the authoritative server version (the source reference code deliberately **does not call `.undo()`**, which can overwrite overlapping edits). On `412`, keep unsaved form text and offer Reload/Compare; **never blindly retry** with a new ETag.
7. With an app-wide per-WorkItem mutation lock you _may_ use `.undo()` for immediate rollback; without that guarantee, invalidate and refetch. The source UI hook prevents duplicate mutations **from one control**, not from every control/tab.

For a _pure reorder_ (within same column), use dedicated `/items/{iid}/reorder`, passing `expectedGroupStatusId` and neighbor IDs. For _moving to another status_ followed by reorder, coordinate the two commands or add a dedicated atomic move-and-order backend command before implementing cross-column drag/drop. Two independent commands can briefly produce inconsistent order and require reconciliation. **Do not assume a status transition also updates Kanban rank.**

## 7. Error handling / UI mapping

All errors use `application/problem+json` with `status`, `code`, `requestId`, `detail`, optional `errors[]`. Show `requestId` in support/debug UI. Do not branch on English/Russian error text.

| HTTP          | UI response                                                          | Retry?                                          |
| ------------- | -------------------------------------------------------------------- | ----------------------------------------------- |
| 400 / 422     | Map `errors[].pointer` to field names; preserve user form input      | only after correction                           |
| 401           | Clear private caches, redirect/login flow                            | **no automatic replay**                         |
| 403           | Disable action / show insufficient permissions; refresh capabilities | no                                              |
| 404           | Not found or hidden; generic not-found screen                        | no                                              |
| 409           | Domain conflict: invalid transition, archived project, etc.          | user must change action                         |
| 412           | Version conflict: show latest server value / compare & reapply       | never blindly                                   |
| 428           | Missing `If-Match`: implementation bug, log & fetch ETag             | request must be fixed                           |
| 429           | Honor `Retry-After`; expose delay                                    | safe GET after delay; writes only if idempotent |
| 5xx / network | Retry UI and telemetry                                               | GETs backoff; mutations only with stable key    |

With .NET `ProblemDetails`, ensure a consistent translation from validation failures / exceptions / authorization handlers. Ordinary ASP.NET Core validation payloads don't necessarily include our custom `code` / `errors[].pointer`; map them centrally in backend middleware/filters and verify via contract tests.

## 8. ETags and command input contracts

Canonical API response fields include both `etag` in DTO and HTTP `ETag` (exact header preferred for detail). **Never use `version.toString()` as `If-Match`.**

```http
PATCH /api/v1/items/ITEM_ID
If-Match: "opaque-strong-etag"
X-CSRF-Token: REQUEST_TOKEN
Content-Type: application/json

{"title":"Better title"}
```

```http
POST /api/v1/items/ITEM_ID/transitions
If-Match: "opaque-strong-etag"
Idempotency-Key: 68cb9a60-4d73-4cc6-b118-5ead44c6573c
X-CSRF-Token: REQUEST_TOKEN
Content-Type: application/json

{"toStatusId":"STATUS_ID"}
```

`PATCH` must not change `statusId`, `projectId`, `version`, `key`, or `workspaceId`. Dedicated commands implement business operations. A failed command must not leave the audit/outbox or associated resources partially modified.

## 9. OpenAPI → TypeScript generation strategy

**Recommended:** ASP.NET Core becomes the canonical publisher of `/openapi/v1.json` (or a versioned schema artifact) once its implementation exists; do _not_ hand-maintain a second incompatible frontend interface definition. The current draft `docs/specification/openapi-p0-core.yaml` is the initial review baseline.

The project already includes Redux Toolkit and React Redux. Once the backend contract is reviewed, evaluate and install code-generation tooling with npm. A future generation command (tool not currently installed) would be:

```bash
npx openapi-typescript docs/specification/openapi-p0-core.yaml \
  -o src/shared/api/generated/schema.d.ts
```

Use the backend-published schema when implementing endpoints; the draft path above is only a review baseline.

Use generated aliases such as:

```ts
import type { components } from '@/shared/api/generated/schema';
export type TWorkItemDetail = components['schemas']['ItemDetail'];
export type TCreateWorkItem = components['schemas']['CreateItem'];
```

For full endpoint-hook generation, `@rtk-query/codegen-openapi` is supported. However, the draft currently has technical IDs like `post_items_iid_transitions`; first rename `operationId`s to stable semantic names (`transitionWorkItem`, `createProject`) or use an explicit transformer. Generated basic hooks need **enhanceEndpoints**/hand-authored overrides for precise tags, `If-Match` headers, idempotency, optimistic mutations, and cache serialization. Do not edit a generated file by hand.

Keep a CI check to regenerate types and fail on diff. Test the published .NET OpenAPI against frontend expectations; OpenAPI _structural_ validation alone cannot prove backend actually behaves as documented.

## 10. .NET backend handshake / acceptance questions

| Question             | Contract owner     | Decision to confirm                                                                     |
| -------------------- | ------------------ | --------------------------------------------------------------------------------------- |
| Cookie auth settings | Backend + Infra    | name, Path/Domain, SameSite, HTTPS, session lifetime                                    |

| CSRF validation      | Backend            | unsafe endpoints incl. login/logout, origin checks, ProblemDetails errors               |
| Concurrency          | Backend            | ETag for reads/details/lists, strong opaque tags, 412/428 semantics                     |
| Idempotency          | Backend            | key scope, persistence window, replay response/body, conflict code                      |
| Kanban rank          | Backend            | atomic cross-column move+reorder or explicit sequencing                                 |
| Query filters        | Backend            | OpenAPI YAML currently omits documented P0 status/assignee/sort query params            |
| Auth refresh         | Backend            | no refresh assumed in v0.1; add only after security design                              |
| Realtime             | Backend + Frontend | SSE/SignalR transport remains an open P1 decision, permission revocation, cursor resync |
| Files                | Backend            | upload session and signed URL handling, expiry and access checks                        |
| Observability        | Both               | X-Request-Id trace, logging redaction, source maps, safe error codes                    |

## 11. Testing strategy

**API unit tests:** `baseApi.prepareHeaders` (CSRF only on unsafe), 401 clears cache, status/ProblemDetails mapping, correct `If-Match`/`Idempotency-Key` headers, no blind write retry.

**Actual-backend integration acceptance:** list/detail caches, create invalidation, transition optimism success and 412 rollback, a paginated second page, mutation of a filtered-out item, permissions revocation, logout/tenant switch.

**.NET contract tests:** backend returns required fields (including `etag`), uses `application/problem+json`, 403/404 policy, 412/428 concurrency, true idempotent replay, CSRF errors, correct list cursor behavior.

**Playwright E2E:** login + CSRF, Workspace switch isolation, create Task, drag between statuses, conflicting edit, project archived, revoked access, multiple tabs.

**Quality gates:** TypeScript strict + ESLint + unit tests + OpenAPI validation + backend integration tests. In E2E tests verify `Set-Cookie` and `ETag` survive the same-origin proxy.

## 12. Proposed implementation order

1. Agree .NET cookie + CSRF + error and ETag protocol (add `/auth/csrf` to OpenAPI).
2. Wire same-origin ingress or local rewrite; verify cookies/headers over HTTPS.
3. Implement baseApi, Provider/store, user session handling, ProblemDetails mapper.
4. Implement workspace and project queries with cache tags.
5. Implement WorkItem list/detail/create/edit/transition; add status and reorder commands.
6. Add UI forms with Zod validation and hook-level command wrappers.
7. Add client-logic tests and actual .NET contract tests; only then optimize Kanban multi-cache optimistic updates.
8. Generate DTOs from ASP.NET Core OpenAPI, enforce generated-type drift checks.
9. Add comments, attachments, notifications and search.
10. Add the agreed realtime transport, Scrum and P1/P2 modules incrementally without creating another API slice.
